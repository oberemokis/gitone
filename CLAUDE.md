# gitone

## Код

Устройство и правила против связанности описаны в `docs/architecture.md`, граф пакетов проверяет `architecture_test.go`. Новый пакет сначала получает место в графе и в таблице теста, потом код.

Команды: `make lint` (`go vet` и `gofmt`), `make test`, `make build`, `make run`. Те же `lint`, `test` и `build` гоняет CI.

## Коммиты

Формат первой строки здесь Conventional Commits по-русски: `<тип>(<область>): <результат>`. Это перекрывает формат первой строки из скилла `oberemokis-skills:commit`, всё остальное из него действует как есть: тело объясняет причину, автор только пользователь, хуки не обходятся.

- Тип: `feat` новая возможность, `fix` исправление, `refactor` перестройка без смены поведения, `perf` скорость, `test` только тесты, `docs` только документация, `chore` зависимости, CI, конфиги.
- Область: пакет, в котором живёт правка (`git`, `diff`, `tui`, `config`), либо `ci` и `docs`. Правка через весь репозиторий идёт без области: `docs: план функций`.
- Результат: одна фраза по-русски со строчной буквы, без точки, что стало, а не что сделано с файлами: `feat(tui): категории клавиш в справке`.
- Ломающее изменение формата конфигов: `!` перед двоеточием (`feat(config)!: клавиши массивом`) и в теле строка `BREAKING CHANGE:` с тем, что сломается у пользователя.

Номер задачи в коммит не пишется: связь с задачей держит ветка и пул-реквест.

## Ветки

`main` единственная долгая ветка. Прямой push в неё закрыт: изменение приходит только пул-реквестом, слияние ждёт зелёной работы «проверки» из `.github/workflows/ci.yml`.

Ветка рождается из задачи на GitHub и носит имя `<тип>/<номер задачи>-<имя>`: тип тот же, что у коммитов (метка `feature` даёт `feat`, метка `bug` даёт `fix`), имя латиницей в kebab-case, два-четыре слова. У задач имя уже записано внизу строкой «Ветка для разработки:», его берёшь как есть.

Корень репозитория делят несколько сессий сразу. Ветка живёт в своём worktree рядом с репозиторием, корень остаётся на той ветке, где был: переключение в корне уносит чужую незакоммиченную работу и подменяет код под соседней сессией.

1. Задача. Номер называет человек, иначе порядок берётся из дорожной карты #1. Если задачи под изменение нет, предложи завести её с меткой типа, `size: S|M|L` и `area: …` и дождись ответа: ветка появляется только после задачи.
2. Открытые вопросы задачи закрываются до кода. Задача с пометкой «До работы: допрос» начинается с `/oberemokis-skills:grill`, его решения дописываются в задачу.
3. Ветка и worktree одной командой: `git fetch origin`, затем `gh issue develop <номер> --name <ветка> --base main --checkout --worktree ../gitone-<номер>-<имя>`. Готово, когда `gh issue develop --list <номер>` показывает ветку, `git -C ../gitone-<номер>-<имя> branch --show-current` печатает её имя, а `git status` в корне такой же, как до шага.
4. Перед пул-реквестом `make lint` и `make test` в worktree: это те же проверки, что в CI.
5. Пул-реквест. `gh pr create --base main --head <ветка>`, заголовок в формате первой строки коммита, в описании `Closes #<номер>`: слияние само закроет задачу.
6. После слияния. `git worktree remove ../gitone-<номер>-<имя>` и `git branch -d <ветка>`.

## Задачи

Задача пишется по образцу уже заведённых: что и зачем, «Решения (допрос)» с отвергнутыми вариантами и причиной отказа, «Случаи» (из них получаются тесты), «Швы», «Открытые вопросы» с рекомендацией, строка «Ветка для разработки». Эпик собирает задачи одной темы и ссылается на дорожную карту #1.

План живёт в задачах, а не в репозитории: в документах он устаревает молча и расходится с задачами.
